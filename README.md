# Task Management API

A backend REST service for managing tasks, with user authentication,
built for Task 1 of the Redynox Python Developer Internship.

## Tech stack

- **Python 3.12**
- **FastAPI** — web framework / REST endpoints
- **SQLAlchemy** — ORM
- **SQLite** — database (swappable for MySQL/PostgreSQL by changing one
  connection string in `app/database.py`)
- **Pydantic** — request/response validation
- **JWT (python-jose) + bcrypt** — authentication

## Project structure

```
task1_task_management_api/
├── app/
│   ├── main.py           # FastAPI app, router registration, error handlers
│   ├── database.py       # SQLAlchemy engine/session setup
│   ├── models.py         # ORM models: User, Task (1:N relationship)
│   ├── schemas.py        # Pydantic request/response schemas
│   ├── auth.py           # Password hashing + JWT token handling
│   ├── crud.py           # Database query layer
│   └── routers/
│       ├── auth.py       # /auth/register, /auth/login
│       └── tasks.py      # /tasks CRUD endpoints
├── requirements.txt
├── test_api.py            # Live test suite exercising every endpoint
├── make_screenshots.py    # Generates screenshots/ from the test transcript
├── testing_log.json/.txt  # Captured request/response transcript
└── screenshots/            # Testing evidence (see report)
```

Code structure explanation: `main.py` only wires things together and
owns error handling; `routers/` only knows about HTTP concerns (status
codes, request parsing); `crud.py` is the only place that touches the
database session directly; `schemas.py` is the validation boundary
between the outside world and `models.py`. This separation is what the
task calls "structured project architecture" — each file has one job.

## Setup

```bash
pip install -r requirements.txt
uvicorn app.main:app --reload
```

The API is then available at `http://127.0.0.1:8000`, with interactive
Swagger docs at `http://127.0.0.1:8000/docs` and ReDoc at `/redoc`.

## Database schema

```
users                          tasks
------------------------       ------------------------------
id (PK)                        id (PK)
username (unique)              title
email (unique)                 description
hashed_password                status      (enum: pending / in_progress / completed)
is_active                      priority    (enum: low / medium / high)
created_at                     due_date
                                created_at
                                updated_at
                                owner_id (FK -> users.id, cascade delete)
```

One user has many tasks (`User.tasks`); each task belongs to exactly
one user (`Task.owner`) and is only visible to its owner.

## API Reference

| Method | Endpoint | Auth required | Description |
|---|---|---|---|
| GET | `/` | No | Health check |
| GET | `/health` | No | Health check |
| POST | `/auth/register` | No | Create a new user account |
| POST | `/auth/login` | No | Log in, returns a JWT access token |
| POST | `/tasks` | Yes | Create a task |
| GET | `/tasks` | Yes | List the current user's tasks (supports `?status_filter=` and `?priority=`) |
| GET | `/tasks/{id}` | Yes | Get a single task |
| PUT | `/tasks/{id}` | Yes | Update a task (partial updates supported) |
| DELETE | `/tasks/{id}` | Yes | Delete a task |

Authenticated requests send `Authorization: Bearer <token>` using the
token returned by `/auth/login`.

### Status codes used

- `200 OK` — successful GET/PUT
- `201 Created` — successful POST (register, create task)
- `204 No Content` — successful DELETE
- `400 Bad Request` — duplicate username/email
- `401 Unauthorized` — missing/invalid token, wrong login credentials
- `404 Not Found` — task doesn't exist or doesn't belong to the caller
- `422 Unprocessable Entity` — request body fails validation
- `500 Internal Server Error` — unexpected/database errors (caught by
  a global exception handler so clients never see a raw traceback)

## Testing

`test_api.py` runs a live server and exercises every endpoint above,
including the error paths (duplicate registration, invalid input,
wrong password, missing task, unauthorized access) — 18 real requests
in total. `testing_log.json` / `testing_log.txt` are the captured
transcript, and `screenshots/` (generated by `make_screenshots.py`)
turns that transcript into visual evidence for the report.

```bash
# In one terminal
uvicorn app.main:app

# In another
python test_api.py
python make_screenshots.py
```
